# Parleywise 复核工作台：UX 与技术设计

## 统一工作区（2026-11-24）

以对话为默认入口：左侧集中工作区导航、最近对话和设置；主区域直接提供输入框，不要求用户先创建空会话。新建审查和审查记录从对话首页进入，审查任务仍使用原文与逐条意见并列的专门视图，以保留证据定位和人工决策。

发送时提示处理中，失败保留输入以便重试；回车发送、Shift+回车换行。个人记忆与工作区共享的项目记忆独立管理，发送时须逐条选择，页面提示所选内容会发送至已配置的模型网关。会话压缩只更新当前会话摘要，支持查看和修订，原始消息不删除；MCP 页面仍明确标识为只保存配置，未连接工具。

## 要验证的问题
合规人员先看 AI 初审意见再终审，能否在**不增加漏审**的前提下，把单份材料的审查时间砍半。
所以界面除了“好用”，还必须顺手记下三类数据：
1. **耗时**：每份材料的有效审查时长（页面可见且有操作；空闲 2 分钟后停止计时）。
2. **AI 意见质量**：每条意见被采纳 / 修改 / 驳回，驳回原因是什么。
3. **漏审**：审核人自己发现、AI 没报的问题（在原文中划选添加），这是 AI 漏报的直接证据。

对照组：上传时可勾选“对照组（不显示 AI 意见）”，同一个界面、同样计时，审核人只靠自己标注问题。
试点时把材料随机分到两组，就能比较有 AI / 无 AI 的耗时和发现问题数。

## 用户流程
```
工作台（材料列表）
  └─ 新建审查：粘贴文本 或 拖入 .txt/.md/.docx/.pdf → 选材料类型（公募/私募）→ 提交
       └─ 处理中：关键词初筛 → 模型初筛 → 模型复核 → 校验（约 1 分钟，页面显示当前阶段）
            └─ 复核页
                 左：原文，问题片段按严重度高亮并编号；点击高亮跳到对应意见
                 右：意见卡片（按原文片段合并），每条规则意见：采纳 / 修改 / 驳回(必选原因)
                 划选原文 → “添加 AI 漏报的问题”→ 选规则 → 写说明
                 顶栏：进度 3/5 · 计时 · 完成审查（选结论：通过 / 修改后通过 / 不通过）
                      └─ 审查报告：可打印/存 PDF，另可导出 Markdown、JSON
  └─ 度量：采纳率、驳回原因分布、人工补充（漏报）数、平均耗时，AI 组 vs 对照组
```

## 交互要点
- 键盘优先：`J/K` 上下切换意见，`A` 采纳，`R` 驳回，`E` 修改，`Esc` 取消。合规人员一天看几十份，鼠标来回点很累。
- 驳回原因固定为可统计的选项：不构成违规 / 规则不适用 / 片段定位不准 / 与其他意见重复 / 其他（填说明）。
- 一处原文片段可能同时违反多条规则，卡片里逐条决定，主规则（严重度最高）在前。
- 每条意见都显示规则编号、条款出处、规则说明（展开），并标明“规则说明为转述，以原文为准”。
- 决定可随时改；完成审查后锁定，可“重新打开”。
- 报告只列采纳/修改的意见和人工补充的问题，驳回的放附录，便于留档。

## 技术选型（单人可维护）
- 后端：FastAPI + SQLite（标准库 sqlite3），直接 import 现有 `review.py`，不复制流水线代码。
  审查任务在后台线程执行，状态写库，前端轮询。
- 前端：无构建步骤的原生 HTML/CSS/JS（`app/static/`），由 FastAPI 直接托管。没有 node_modules，没有打包。
- 数据：`app/data/parleywise.db`（已 gitignore）。材料原文只存本机；送去模型的内容经 LiteLLM 网关。
- 登录：账号用命令行管理（`python -m app.auth`），scrypt 口令哈希，HttpOnly 会话 Cookie；审核人姓名取自登录身份，审计日志记录每个操作者。
- 启动：`./run.sh`，浏览器打开 http://127.0.0.1:8000 。试点部署见 `app/DEPLOY.md`。
